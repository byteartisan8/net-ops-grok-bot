## The template: intent vs observed

**Polling.** One SNMP agent item, `netsim.snmp.walk` = `walk[]` over the 7 cpwVcTable columns the checks read
(PeerAddr, ID, RemoteIfMtu, Name, Descr, AdminStatus, OperStatus) and 6 IF-MIB columns, every `{$NETSIM.WALK.INTERVAL}`
= 60 s. Everything else is dependent on it (or a trap/internal item). Zabbix 8.0's walk text is numeric OIDs, numeric
enums, quoted strings, and `Hex-STRING: 0A FF 00 01` for the 4-octet `cpwVcPeerAddr` (checked in `checks_snmp.c`).

**Intent: "Expected PWs (NetBox spec)"** — the cleanest 8.0 way to run discovery on a macro is a **Script-type
discovery rule** whose parameters are the macros (`spec1 = {$NETSIM.PW.SPEC}`, `spec2 = {$NETSIM.PW.SPEC.2}`, …): the
script (`js/pw_spec_discovery.js`) parses and concatenates them (failing loudly on bad JSON or duplicates) and
returns the rows; LLD macro paths map `{#SERVICE}`, `{#ROLE}`, `{#VC_ID}`, `{#EXPECTED_PEER}`,
`{#EXPECTED_PEER_HOST}`, `{#CUSTOMER}`, `{#AC}`, `{#VCNAME}`. No network access, cheap, re-run on demand (sync, and
the check-now script on config/boot traps); lost rows are deleted immediately, so a PW removed from NetBox takes its
items, triggers and problems with it. Per expected PW:

* `netsim.pw.row[SVC,role]` (8.0 **JSON** value type), dependent on the walk master: JavaScript
  (`js/walk_lib.js` + `js/pw_row.js`) finds the row whose `cpwVcName == "SVC:role"` and returns
  `{present, index, oper, admin, peer (dotted quad), vc_id, remote_mtu, customer}`, or a defined absent value
  (`present 0`, `peer "absent"`, zeros) — never an error, so `missing` is reliable;
* `present`, `oper`, `admin`, `peer`, `vcid`, `remote_mtu` (JSONPath from the row; value maps include `0 = absent`)
  and `spec_diff` (JavaScript: `matches NetBox` / `absent` / e.g. `peer 10.255.0.2, NetBox expects 10.255.0.1 (hub-a)`).

The row is one JSON parse per PW per walk; the field items are trivial. (They are dependent on the walk through the
row item, not each directly on the walk: the lookup runs once, and the row item is what the bot can read.)

Trigger prototypes, exactly contract §9.2, each tagged `scope=l2vpn-pw`, `service`, `pw_role`, `customer`, `host`,
`check`, `vcid`, `peer`:

| check | expression | severity | event name (examples are real) |
|---|---|---|---|
| missing | `last(present)=0` | High | `SVC-0004 backup on spoke-3: PW missing, NetBox expects VC ID 2004 to 10.255.0.2 (hub-b) on GigabitEthernet0/0/1.301` |
| oper | `last(present)=1 and last(oper)<>1` | High | `SVC-0002 primary on hub-a: PW down (2), VC ID 1002 to 10.255.1.2 (spoke-2)` |
| spec | `last(present)=1 and (last(peer)<>"{#EXPECTED_PEER}" or last(vcid)<>{#VC_ID})` | Average | `SVC-0002 primary on spoke-2: peer 10.255.0.2, NetBox expects 10.255.0.1 (hub-a)` |

`oper` and `spec` depend on `missing` (and require the row in their expression, so they can never double-alarm with
it). The `spec` event name is an expression macro, `{?last(/{HOST.HOST}/netsim.pw.spec_diff[...])}`, so it names
exactly what differs (peer, VC ID or both) — the contract's example string is produced verbatim.

**Observed: "PW table (device)"** — dependent discovery on the walk: SNMP walk to JSON (`{#VCNAME}`, `{#VCID}`,
`{#PEER}`, `{#CUSTOMER}`, `{#SNMPINDEX}`) plus JavaScript turning the hex peer into a dotted quad. Items: oper, peer,
VC ID and "in NetBox spec" (SNMP walk value + JavaScript that reads `{$NETSIM.PW.SPEC}` and its chunks — macro
values are JSON lists, i.e. valid JavaScript literals). Trigger `unexpected` (Warning, `scope=l2vpn-unexpected`,
`check=unexpected`): `SVC-0099:primary on spoke-1: PW not in NetBox (VC ID 1099 to 10.255.0.1)`. Not mapped into
the BSM.

**Interfaces** — dependent discovery over IF-MIB (`{#IFNAME}`, `{#IFDESCR}`, `{#IFALIAS}`): oper/admin status, MTU;
trigger "down" (admin up, oper not up; Average, `scope=interface`, not in the BSM).

**Traps** (`SNMP_TRAP` items, matched by numeric OID on the `snmpTrapOID.0` varbind, e.g.
`snmptrap["\.1\.3\.6\.1\.6\.3\.1\.1\.4\.1\.0 = \.1\.3\.6\.1\.4\.1\.9\.10\.106\.2\.1(\s|$)"]`): cpwVcDown, cpwVcUp
(`trap=pw`), ciscoConfigManEvent (`trap=config`), coldStart (`trap=boot`), and `snmptrap.fallback`. Their triggers,
`length(last(...))>0 and nodata(...,{$NETSIM.TRAP.HOLD})=0`, generate **one problem event per trap** (multiple
problem events), Information, tags `scope=l2vpn-trap`, `trap=…`, and recover 30 s after the last trap.

**Availability:** `zabbix[host,snmp,available]` every 10 s; High "SNMP agent unreachable" when it is 0 for 30 s.

### The macro limit and the overflow mechanism

`{$NETSIM.PW.SPEC}` is a host macro, and **Zabbix 8.0 limits macro values to 2048 characters** (`hostmacro.value
varchar(2048)` in the 8.0.0rc1 schema). One entry is ~170 characters, so a macro holds ~12 PWs: every lab host fits
(hub 1016 characters), a scale-topology hub does not. The next-cleanest option keeps the contract's format: the sync
splits a long spec into chunks of ≤ 2048 characters, `{$NETSIM.PW.SPEC}` (exactly `pw_spec_macro_value()` whenever it
fits) and `{$NETSIM.PW.SPEC.2}` … `{$NETSIM.PW.SPEC.8}` (template defaults `[]`), which the discovery script and the
`unexpected` check concatenate in order: ~96 PWs per host; beyond that the sync refuses with an error. Plain numbered
macros rather than macro contexts: a context macro that is not defined falls back to the context-less macro, which
would duplicate the first chunk. Tested: unit tests chunk a 60-PW hub; a live test puts one extra PW into hub-b's
`{$NETSIM.PW.SPEC.2}`, sees it discovered and `missing`, and the next sync prunes it. (Rejected: the spec in an
inventory field — 64 KB and usable in script parameters, but the contract and the bot read the macro.)

## Trap → poll ("check now")

1. A device sends a trap within ~0.14 s of a transition (02's measurement); snmptrapd writes it to the trap file.
2. The SNMP trapper reads it (≤ ~1 s): the trap item gets the value, the trap trigger a new problem event.
3. Action **NetSim: SNMP trap -> check now** (conditions: template `NetSim L2VPN PE SNMP` and event tag `trap`;
   no pause for symptoms or maintenance) runs the global webhook script **NetSim: check now**
   (`js/check_now.js`) on the event's host. The escalator is notified immediately on new escalations.
4. The script calls the API with the secret global macro `{$NETSIM.ZABBIX.API.TOKEN}`: `item.get` for the walk
   master (`trap=pw`), plus `discoveryrule.get` for the non-dependent discovery rules (the spec discovery) on
   `trap=config|boot` — the dependent "PW table" and interface discoveries are refreshed by the walk value itself —
   then `task.create` (type 6, "execute now").
5. The server's **task manager** picks the tasks up and reschedules the items; the walk runs; every dependent item,
   check and the BSM follow.

**Finding (8.0.0rc1 source):** `task.create` only inserts rows into the `task` table (`CTask::createTasksCheckNow`),
and the task manager processes them on a **fixed 5-second grid** (`ZBX_TM_PROCESS_PERIOD 5`, sleeping to the next
multiple of 5 s of wall-clock time, `taskmanager_server.c`); it wakes early only for a local runtime-control command
(proxy config reload), which no API reaches. So step 5 adds a uniform 0–5 s wait to every check-now. Measured (36
real cpwVcDown/cpwVcUp traps over three runs, from cutting/restoring the core path spoke-3↔hub-b; walk interval raised
to 1 h on the two hosts during the test, so every walk value seen is a check-now): trap value in Zabbix → walk value
**median 2.9 s, mean 3.1 s, p90 5.2 s, max 5.9 s; 30 of 36 ≤ 5 s**. Within a run the samples sit on a 1 s grid
(e.g. 1.9, 2.9, 3.9, 4.9, 5.9) — the task manager's phase. The contract's "≤ 5 s" holds at the median and for 83 %
of traps; the worst case is 5 s + trapper/escalation/poll time (~1 s) by construction.
The contract change log records this bound and suggests e2e assert median ≤ 5 s and every sample ≤ 7 s (as the
integration test does). Rejected workarounds: polling the walk every few seconds (contract: 60 s), a second
"Script" operation running `zabbix_server -R` to wake the task manager (needs `EnableGlobalScripts=1` and leans on a
side effect).

The faster end-to-end path in practice is **fault → BSM** (budget 10 s): the trap from *either* end starts a
check-now, measured 1.1–5.2 s (power-off: 4.5 s).

## BSM sync (`zabbix-sync`)

Input: the BSM spec from NetBox (`netsim_netbox.intent`: one snapshot with the read-only token, then
`bsm_spec(...)`), or `--source topology`; validated against `contract/bsm-spec.schema.json`; the NetBox and topology
specs are equal after `normalized()`. Hosts come from the same snapshot (devices with platform `netsim-clixon`,
`primary_ip4` = SNMP address) — inventory (name, type = role, vendor, model, OS = platform, location = site,
deployment status, NetBox URL, loopback) is filled from NetBox.

Steps, each a diff against what Zabbix has (printed as a plan; `--dry-run` writes nothing):

1. **Spec macros** on every provisioned host (both ends of every leaf), chunked as above; entries gone from NetBox
   are pruned by rewriting the value, unneeded overflow macros are deleted.
2. **BSM tree**, contract §9.4: `L2VPN` → customers → `SVC-xxxx (spoke)` → PW leaves. Every node gets the spec's tags
   (+ `managed_by=netsim-zabbix`; services also `sla_tier`) and the spec's description (NetBox URL; for leaves a/z-end
   host, AC, VC ID, expected peers). Status calculation in 8.0 terms:

   | node | main rule | additional rules | problem tags |
   |---|---|---|---|
   | root, customer | most critical of child services | — | — |
   | service (`redundant-pair`) | set status to OK | ≥ 2 children ≥ High → Disaster; ≥ 1 child ≥ Average → Warning | — |
   | PW leaf | (no children) | — | `scope=l2vpn-pw`, `service`, `pw_role` (equals) |

   8.0's additional rules can only *raise* the main rule's status and the highest match wins, so `redundant-pair`
   needs "set status to OK" as its main rule (with "most critical", one High PW would make the service High).
   Nodes are matched by name; new nodes are created parent-first, changed ones updated (fields compared:
   rule, sort order, description, tags, problem tags, status rules, parent), and managed nodes that are no longer in
   the spec deleted (renames are delete + create). Hand-made services are never touched.
3. **SLAs** `L2VPN gold` (99.95 %) and `L2VPN silver` (99.9 %), monthly, UTC, selecting services by tag `sla_tier`;
   `effective_date` (required by 8.0) = the creation day, kept afterwards.
4. **Refresh** (hosts whose spec changed): wait for the server's configuration cache (5 s), execute now the spec
   discovery, wait until the discovered PW items equal the spec, wait for the cache again, execute now the walk.
   A NetBox change is checked ~15–25 s after `zabbix-sync` starts (measured 21–22 s sync, 23.3 s to Disaster for a new
   service) instead of after the next discovery and poll intervals (53 s before this step existed).
5. **Map** last (its link indicators are the discovered triggers).

A second run makes **0 changes**; so does `zabbix-provision`. `sync()` is importable for lab-api (see notes).

## Dashboard and map

## Bootstrap and the API user

`zabbix-bootstrap` (run by `make zabbix-up` / `zabbix-provision`) logs in as Admin — with `ZABBIX_ADMIN_PASSWORD`, or
the factory `zabbix` once, which it then replaces — and does what only a Super admin may: host/template groups, the
API user and token, global macros, the webhook script. Everything else runs with `ZABBIX_API_TOKEN`:

## Known limitations

- **Check-now worst case ~6 s** (5 s task-manager grid, not configurable in 8.0); median 2.9 s, 83 % ≤ 5 s.
- A PW **added on a device** surfaces as `unexpected` only after the next regular walk (≤ 60 s): the config trap's
  re-poll lets "PW table" discover the row, but Zabbix does not re-dispatch that value to the items it just
  created. Changes to *expected* PWs (intent items exist already) are not affected.
- When a device is unreachable its own items keep their last values (no `missing`/`oper` from it); its PWs are still
  checked from the other end (BSM in ~5 s). Its own "SNMP agent unreachable" needs a failed poll first: up to the next
  60 s walk + 15 s unreachable period + the trigger's 30 s window (measured 72 s); a faster per-device ping would need a
  second SNMP item, which the contract's "everything else is dependent on the walk" rules out.
- Observed items are keyed by `cpwVcIndex`; the devices keep indexes stable (contract §7). If indexes were
  reassigned, an `unexpected` problem raised during the change could keep the previous row's name in its tags.
- Traps are hints only; the trap trigger's 30 s `nodata` recovery means several traps in 30 s produce several events
  of one open problem chain (by design: one event per trap).
- Pre-release software: 8.0.0rc1 (see the planned bump). The template is regenerated from code, so a format change in
  GA shows up in `importcompare` and the unit test.
- `zabbix-sync` with a refresh takes ~15–25 s when a spec changed (it waits for the server); `--no-refresh` returns in
  ~2 s and leaves discovery to its 1-minute interval.
